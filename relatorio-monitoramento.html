Arquitetura de alertas

  • 1 componente cai → alerta daquele componente (você vê qual).
  • Todos caem → dispara a agregada "<App> fora do ar" e as individuais ficam suprimidas por dependência → 1 alerta só, sem flapping.
Decisão técnica: usamos trigger dependency (não event correlation). O teste no host TESTE-CORRELACAO provou que correlação "close old events" causa flapping em condição persistente (fecha o evento e a trigger reabre). A dependência suprime na origem. Validado: as 6 triggers do Totvs de teste apontam corretamente para "Totvs fora do ar".

Comportamento quando o agente / host cai

Quando o agente ou o host inteiro cai, você recebe ~1 alerta ("Zabbix agent is not available") — não há chuva de "serviço parado".

O que caiO que dispara
Agente / host inteiroSó "Zabbix agent is not available". As triggers de serviço congelam em OK e não disparam.
1 serviço (agente vivo)A trigger daquele serviço (identifica qual).
Todos os componentes de um app1 trigger agregada "<App> fora do ar"; individuais suprimidas por dependência.
Por quê: as triggers usam last(). Sem dado novo (agente fora), o last() mantém o último valor (serviço OK) → a trigger não dispara. A tempestade só ocorreria com nodata(), que não é usado. Confirmado via API: todos os hosts (Windows e Linux) têm o gatilho de agente indisponível.
Atenção (Windows): o template oficial Windows by Zabbix agent tem duas triggers "agent is not available" (Average + High) → host Windows dá 2 alertas na queda do agente. Para reduzir a 1, desabilite a de severidade Average.
